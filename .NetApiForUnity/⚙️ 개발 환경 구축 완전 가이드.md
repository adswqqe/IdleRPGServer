# ⚙️ 개발 환경 구축 완전 가이드 - Unity 개발자를 위한 서버 개발 시작하기

> **대상**: Unity 개발자 (GUI 중심 설정 선호)  
> **목표**: 서버 개발을 위한 완벽한 개발 환경 구축  
> **특징**: 콘솔 명령어 최소화, JetBrains Rider 중심 워크플로우  
> **시간**: 약 2-3시간으로 완전한 환경 구축 가능

---

## 🎯 왜 이 가이드가 Unity 개발자에게 특별한가?

Unity에서 개발하시면서 이런 경험들이 있으셨을 것입니다. Unity Hub에서 프로젝트를 생성하고, Package Manager에서 필요한 패키지를 설치하며, Build Settings에서 플랫폼별 설정을 관리하는 것들 말입니다. 이 가이드는 그런 Unity 경험을 그대로 활용할 수 있도록 설계되었습니다.

서버 개발 환경 구축도 Unity와 본질적으로 같습니다. IDE를 설치하고(Unity Hub → JetBrains Rider), 필요한 도구들을 추가하며(Package Manager → NuGet), 실행 환경을 설정하는(Build Settings → Docker Compose) 과정입니다. 차이점은 더 강력하고 확장 가능한 도구들을 사용한다는 것뿐입니다.

## 🛠️ 1단계: 필수 소프트웨어 설치 (Unity Hub처럼 쉽게)

### JetBrains Rider - 서버 개발의 Unity Editor

Unity를 개발하시면서 JetBrains 도구들을 사용해보신 적이 있으시다면, Rider는 매우 친숙할 것입니다. Unity Editor가 게임 개발의 중심이듯, Rider는 서버 개발의 중심이 됩니다.

**Rider 설치 과정**
JetBrains 공식 웹사이트(https://www.jetbrains.com/rider/)에서 다운로드할 수 있습니다. Unity 개발자라면 학생 라이선스나 오픈소스 프로젝트 라이선스를 받을 수 있는 경우가 많습니다. 그렇지 않더라도 30일 평가판으로 충분히 학습할 수 있습니다.

Rider를 선택하는 이유는 Unity Editor와 매우 유사한 사용자 경험을 제공하기 때문입니다. Project 창, Inspector 창, Console 창이 모두 Unity와 유사한 방식으로 배치되어 있습니다. 특히 IntelliSense(자동완성) 기능은 Unity의 그것보다 훨씬 강력합니다.

### .NET 8 SDK - Unity Runtime의 서버 버전

Unity에서 Mono Runtime이나 IL2CPP를 사용하듯, 서버 개발에서는 .NET Runtime을 사용합니다. .NET 8 SDK는 Microsoft 공식 사이트(https://dotnet.microsoft.com/download/dotnet/8.0)에서 다운로드할 수 있습니다.

Windows에서는 x64 Installer를, macOS에서는 Intel 또는 Apple Silicon용 Installer를 선택하시면 됩니다. 설치가 완료되면 터미널에서 `dotnet --version`을 실행하여 8.0.x 버전이 출력되는지 확인해보세요. Unity에서 About Unity를 확인하는 것과 같은 개념입니다.

### Docker Desktop - Unity Build Settings의 서버 버전

Unity에서 Android, iOS, PC 빌드 설정을 관리하듯, Docker는 다양한 서버 환경을 격리해서 관리합니다. Unity의 Addressable Asset System처럼 리소스를 효율적으로 관리할 수 있게 해주는 도구입니다.

Docker Desktop은 https://www.docker.com/products/docker-desktop/에서 다운로드할 수 있습니다. 설치 후 Docker Desktop을 실행하면 Unity Hub와 유사한 GUI 인터페이스를 볼 수 있습니다. Containers 탭에서 실행 중인 컨테이너들을 확인할 수 있고, Images 탭에서 사용 가능한 이미지들을 관리할 수 있습니다.

### Git과 GitHub - Unity Collaborate의 개선된 버전

Unity에서 Unity Collaborate나 Plastic SCM을 사용하셨다면, Git은 그보다 훨씬 강력한 버전 관리 시스템입니다. Git은 https://git-scm.com/downloads에서, GitHub Desktop은 https://desktop.github.com/에서 다운로드할 수 있습니다.

Unity Collaborate와 달리 Git은 분산 버전 관리 시스템입니다. 각 개발자가 완전한 프로젝트 히스토리를 로컬에 가지고 있어서, 인터넷 연결 없이도 커밋과 브랜치 작업이 가능합니다. GitHub Desktop을 사용하면 Unity Hub처럼 GUI로 모든 작업을 할 수 있습니다.

## 🏗️ 2단계: Clean Architecture 프로젝트 생성 (Unity Template처럼)

### Rider에서 새 솔루션 생성하기

Unity에서 New Project를 생성하듯, Rider에서 새 솔루션을 생성하는 과정입니다. Rider를 실행하고 'New Solution'을 클릭하면 Unity의 템플릿 선택 화면과 유사한 인터페이스를 볼 수 있습니다.

Templates에서 '.NET' 카테고리를 선택하고 'ASP.NET Core Web Application'을 찾으세요. Unity에서 3D Template, 2D Template을 선택하는 것과 같은 개념입니다. 프로젝트 설정에서는 솔루션 이름을 'IdleRPGServer'로, 프로젝트 이름을 'IdleRPG.API'로 설정합니다.

Framework는 반드시 '.NET 8.0'을 선택하세요. Unity에서 Unity 버전을 선택하는 것과 같습니다. Project Type은 'Web API'를 선택하고, 'Enable Docker'와 'Enable OpenAPI support'를 체크합니다. 이는 Unity에서 Target Platform을 설정하는 것과 유사한 개념입니다.

### Clean Architecture를 위한 추가 프로젝트들

Unity에서 Packages 폴더에 다양한 패키지들이 들어가듯, Clean Architecture에서는 여러 프로젝트가 각각의 역할을 담당합니다. 솔루션 탐색기에서 솔루션을 우클릭하고 'Add' → 'New Project'를 선택하세요.

**Domain 프로젝트 생성**
Templates에서 'Class Library'를 찾으세요. Unity Package Manager에서 Library를 찾는 것과 비슷한 과정입니다. 만약 'Class Library'가 바로 보이지 않는다면, 검색 박스에 'library'를 입력하거나 Language 필터에서 'C#'을 선택해보세요. 프로젝트 이름은 'IdleRPG.Domain'으로 설정합니다.

**Application과 Infrastructure 프로젝트도 동일한 방식으로 생성**
'IdleRPG.Application'과 'IdleRPG.Infrastructure'도 같은 방식으로 생성합니다. 이때 Web API 템플릿을 선택하지 않도록 주의하세요. Web API는 웹 서버 프로젝트이고, Class Library는 코드 라이브러리 프로젝트입니다.

### 프로젝트 간 의존성 설정

Unity에서 Assembly Definition을 설정하여 스크립트 간 의존성을 관리하듯, 여기서도 프로젝트 간 의존성을 설정해야 합니다. 각 프로젝트를 우클릭하고 'Manage References'를 선택하면 Unity의 Assembly Definition References와 유사한 화면을 볼 수 있습니다.

IdleRPG.API는 IdleRPG.Application과 IdleRPG.Infrastructure를 참조해야 합니다. IdleRPG.Application은 IdleRPG.Domain만 참조하고, IdleRPG.Infrastructure는 IdleRPG.Domain과 IdleRPG.Application을 참조합니다. 이는 Clean Architecture의 의존성 규칙을 따르는 것입니다.

## 📦 3단계: NuGet 패키지 관리 (Package Manager처럼)

### Rider의 NuGet Manager 활용하기

Unity의 Package Manager에서 패키지를 설치하듯, Rider에서는 NuGet Manager를 사용합니다. 각 프로젝트를 우클릭하고 'Manage NuGet Packages'를 선택하면 Unity Package Manager와 매우 유사한 인터페이스를 볼 수 있습니다.

Browse 탭에서 패키지를 검색하고, Installed 탭에서 설치된 패키지를 관리할 수 있습니다. Unity Package Manager의 In Project, Unity Registry와 같은 개념입니다. 중요한 것은 각 프로젝트에 필요한 패키지만 설치하는 것입니다.

### 프로젝트별 필수 패키지 설치

**IdleRPG.API 프로젝트 패키지들**
Microsoft.EntityFrameworkCore.Design은 Entity Framework의 마이그레이션 도구입니다. Unity에서 Addressable Asset의 Build Pipeline과 유사한 역할을 합니다. Serilog.AspNetCore는 구조화된 로깅을 위한 패키지로, Unity의 Debug.Log보다 훨씬 강력한 기능을 제공합니다. Swashbuckle.AspNetCore는 API 문서를 자동 생성해주는 도구로, Unity의 Documentation Generation과 유사합니다.

**IdleRPG.Infrastructure 프로젝트 패키지들**
Microsoft.EntityFrameworkCore는 객체-관계 매핑(ORM) 프레임워크입니다. Unity의 ScriptableObject가 데이터를 직렬화하듯, Entity Framework는 C# 객체를 데이터베이스 테이블에 매핑합니다. Npgsql.EntityFrameworkCore.PostgreSQL은 PostgreSQL 데이터베이스와의 연결을 담당합니다. Microsoft.EntityFrameworkCore.Tools는 명령줄 도구를 제공합니다.

**IdleRPG.Application 프로젝트 패키지들**
AutoMapper는 객체 간 변환을 자동화해주는 도구입니다. Unity에서 DTO를 Entity로 변환하는 작업을 자동화한다고 생각하시면 됩니다. FluentValidation은 입력 검증을 위한 프레임워크로, Unity의 Attribute 기반 검증보다 훨씬 유연합니다. MediatR은 CQRS 패턴을 구현하기 위한 라이브러리입니다.

## 🐳 4단계: Docker 환경 구성 (Unity Build System처럼)

### Docker Compose 파일 생성하기

Unity의 Build Settings에서 플랫폼별 설정을 관리하듯, Docker Compose는 여러 서비스의 실행 환경을 정의합니다. Rider에서 솔루션 루트에 새 파일을 생성하세요. 솔루션을 우클릭하고 'Add' → 'New Item'을 선택한 후, File Type을 'Text File'로 설정하고 이름을 'docker-compose.yml'로 지정합니다.

Docker Compose 파일은 YAML 형식을 사용합니다. Unity의 Scene 파일이나 Prefab 파일처럼 구조적인 설정을 담고 있습니다. 여기서는 PostgreSQL 데이터베이스, Redis 캐시, pgAdmin 관리 도구를 정의할 것입니다.

```yaml
version: '3.8'

services:
  # PostgreSQL Database - Unity의 PlayerPrefs 확장 버전
  postgres:
    image: postgres:16
    container_name: idlerpg-postgres
    environment:
      POSTGRES_DB: idlerpgdb
      POSTGRES_USER: gamedev
      POSTGRES_PASSWORD: dev123!
    ports:
      - "5432:5432"
    volumes:
      - postgres_data:/var/lib/postgresql/data
    networks:
      - idlerpg-network

  # Redis Cache - Unity의 Object Pool 확장 버전
  redis:
    image: redis:7-alpine
    container_name: idlerpg-redis
    ports:
      - "6379:6379"
    networks:
      - idlerpg-network

  # pgAdmin - Unity Editor의 Inspector 같은 DB 관리 도구
  pgadmin:
    image: dpage/pgadmin4
    container_name: idlerpg-pgadmin
    environment:
      PGADMIN_DEFAULT_EMAIL: admin@idlerpg.com
      PGADMIN_DEFAULT_PASSWORD: admin123
    ports:
      - "8082:80"
    depends_on:
      - postgres
    networks:
      - idlerpg-network

volumes:
  postgres_data:

networks:
  idlerpg-network:
    driver: bridge
```

### Docker Desktop에서 실행하기

Unity의 Play 버튼을 누르는 것처럼, Docker Desktop에서 컨테이너들을 실행할 수 있습니다. Docker Desktop을 실행하고 터미널에서 프로젝트 폴더로 이동한 후 `docker-compose up -d postgres redis pgadmin`을 실행하세요.

-d 옵션은 백그라운드에서 실행한다는 의미입니다. Unity에서 게임을 Build and Run할 때 백그라운드에서 빌드 프로세스가 실행되는 것과 비슷합니다. Docker Desktop의 Containers 탭에서 실행 중인 컨테이너들을 확인할 수 있습니다.

### pgAdmin 웹 접속 설정하기

pgAdmin은 Unity Editor의 Inspector 창처럼 데이터베이스를 시각적으로 관리할 수 있는 도구입니다. 브라우저에서 http://localhost:8082에 접속하면 로그인 화면이 나타납니다. 이메일은 admin@idlerpg.com, 비밀번호는 admin123을 사용하세요.

로그인 후 서버를 추가해야 합니다. Unity에서 Project Settings를 열어 설정하는 것과 비슷한 과정입니다. 좌측 패널에서 우클릭하고 'Create' → 'Server'를 선택하세요. General 탭에서 Name을 'IdleRPG Database'로 설정하고, Connection 탭에서 Host를 'postgres', Port를 5432, Database를 'idlerpgdb', Username을 'gamedev', Password를 'dev123!'로 설정합니다.

## 🔗 5단계: GitHub 저장소 연결 (Unity Collaborate 개선판)

### Rider VCS 통합 활용하기

Unity Collaborate보다 훨씬 강력한 Git 통합을 경험해보세요. Rider 메뉴에서 'VCS' → 'Enable Version Control Integration'을 선택하면 Unity의 Version Control 설정과 유사한 화면이 나타납니다. Git을 선택하고 OK를 누르면 로컬 Git 저장소가 초기화됩니다.

Rider의 VCS 창은 Unity의 Version Control 창보다 훨씬 직관적입니다. 변경된 파일들이 실시간으로 표시되고, diff 기능으로 변경 내용을 시각적으로 확인할 수 있습니다. Unity Collaborate의 그것보다 훨씬 상세한 정보를 제공합니다.

### GitHub 저장소 생성 및 연결

Unity Cloud Build와 연결하듯, GitHub와 연결하는 과정입니다. Rider 메뉴에서 'Git' → 'GitHub' → 'Share Project on GitHub'을 선택하면 저장소 생성 화면이 나타납니다. Unity Cloud Build 설정과 유사한 인터페이스입니다.

Repository name을 'IdleRPGServer'로, Description을 '2D Idle RPG Game Server'로 설정하세요. Private 옵션을 체크하여 개인 프로젝트로 설정할 수 있습니다. Unity Cloud Build에서 빌드 설정을 구성하는 것과 비슷한 개념입니다.

### .gitignore 파일 최적화

Unity에서 .gitignore 파일로 불필요한 파일들을 제외하듯, 서버 프로젝트에서도 제외할 파일들이 있습니다. 솔루션 루트의 .gitignore 파일을 열어 다음 내용을 추가하세요.

```gitignore
# Unity 서버개발 특화 제외 파일들
*.user
appsettings.Development.json  # 개발 설정 보안
logs/                         # 로그 파일들
*.db                         # 로컬 DB 파일
.env                         # 환경 변수
.idea/                       # Rider 설정 파일
bin/
obj/
```

이는 Unity의 Library, Temp 폴더를 제외하는 것과 같은 개념입니다. 개발자마다 다를 수 있는 설정 파일들과 빌드 결과물들을 버전 관리에서 제외합니다.

## 🚀 6단계: 실행 환경 설정 및 테스트

### 연결 문자열 설정하기

Unity의 Player Settings에서 각종 설정을 관리하듯, ASP.NET Core에서는 appsettings.json 파일로 설정을 관리합니다. IdleRPG.API 프로젝트의 appsettings.Development.json 파일을 열어 데이터베이스 연결 정보를 추가하세요.

```json
{
  "Logging": {
    "LogLevel": {
      "Default": "Information",
      "Microsoft.AspNetCore": "Warning"
    }
  },
  "ConnectionStrings": {
    "DefaultConnection": "Host=localhost;Database=idlerpgdb;Username=gamedev;Password=dev123!"
  }
}
```

이는 Unity의 Graphics Settings나 Audio Settings를 설정하는 것과 유사한 개념입니다. 개발 환경에서만 사용할 설정들을 별도로 관리할 수 있습니다.

### Rider 실행 구성 설정하기

Unity의 Build Settings처럼, Rider에서도 실행 구성을 설정할 수 있습니다. Rider 상단의 실행 구성 드롭다운을 클릭하고 'Edit Configurations'를 선택하세요. Unity의 Player Settings 창과 유사한 인터페이스가 나타납니다.

Environment variables에 ASPNETCORE_ENVIRONMENT=Development를 추가하세요. 이는 Unity의 Development Build 설정과 유사한 개념입니다. Working directory가 프로젝트 루트로 설정되어 있는지 확인하고 OK를 눌러 설정을 저장하세요.

### 첫 실행 및 테스트

Unity의 Play 버튼을 누르듯, Rider의 Run 버튼(▶️)을 클릭하세요. 처음 실행하면 방화벽 경고가 나타날 수 있는데, Unity에서 Networking을 사용할 때와 마찬가지로 허용해주시면 됩니다.

브라우저가 자동으로 열리면서 Swagger UI가 표시됩니다. 이는 Unity의 Profiler나 Console 창처럼 개발 중에 API를 테스트할 수 있는 도구입니다. WeatherForecast API가 기본적으로 제공되므로 'Try it out' 버튼을 눌러 테스트해보세요.

## 🔧 7단계: Claude MCP 통합 환경 (선택사항)

### MCP 서버들의 역할 이해하기

Unity에서 여러 패키지들이 각각의 기능을 제공하듯, MCP 서버들도 각각 특별한 역할을 담당합니다. Memory Bank MCP는 학습 내용을 저장하고 동기화하는 역할을, Sequential Thinking MCP는 복잡한 문제를 단계별로 해결하는 데 도움을 줍니다.

Context7 MCP는 최신 라이브러리 문서를 조회할 수 있게 해주고, Filesystem MCP는 프로젝트 파일을 관리합니다. Obsidian MCP는 학습 노트와 연동되며, GitHub MCP는 저장소 관리를 자동화합니다. Unity의 Package Manager처럼 필요에 따라 선택적으로 활용할 수 있습니다.

### 자동화 스크립트 활용하기

Unity에서 Build Script를 작성하여 빌드 과정을 자동화하듯, MCP 환경도 스크립트로 자동화할 수 있습니다. setup-claude-mcp.sh 스크립트를 사용하면 기존 프로젝트에 한 번에 MCP 환경을 추가할 수 있습니다.

sync.sh 스크립트는 집과 회사 환경을 전환할 때 사용할 수 있습니다. Unity Hub에서 프로젝트를 다른 컴퓨터로 이동할 때 설정을 동기화하는 것과 비슷한 개념입니다. 환경변수 기반의 동적 설정 관리를 통해 각 환경에 맞는 최적화된 구성을 사용할 수 있습니다.

## ✅ 완성도 확인 체크리스트

### 필수 소프트웨어 설치 확인

JetBrains Rider가 정상적으로 실행되고 .NET 8 프로젝트를 인식하는지 확인하세요. Unity Editor에서 프로젝트를 열어 정상 동작을 확인하는 것과 같습니다. 터미널에서 `dotnet --version`을 실행하여 8.0.x 버전이 출력되는지 확인하세요.

Docker Desktop이 실행되고 있고, Containers 탭에서 PostgreSQL, Redis, pgAdmin 컨테이너들이 정상 동작하는지 확인하세요. Unity의 Console 창에서 에러가 없는지 확인하는 것과 비슷합니다.

### 프로젝트 구조 및 빌드 확인

Rider의 Solution Explorer에서 4개 프로젝트(API, Domain, Application, Infrastructure)가 모두 표시되고 참조 관계가 올바르게 설정되어 있는지 확인하세요. Unity의 Project 창에서 폴더 구조를 확인하는 것과 같습니다.

Rider에서 Build → Rebuild Solution을 실행하여 모든 프로젝트가 에러 없이 컴파일되는지 확인하세요. Unity에서 전체 프로젝트를 다시 컴파일하는 것과 같은 개념입니다.

### 실행 환경 테스트

Rider에서 Run 버튼을 클릭했을 때 브라우저가 자동으로 열리고 Swagger UI가 표시되는지 확인하세요. Unity에서 Play 버튼을 눌렀을 때 게임이 정상 실행되는지 확인하는 것과 같습니다.

pgAdmin 웹 인터페이스(http://localhost:8082)에 접속하여 데이터베이스 연결이 정상적으로 이루어지는지 확인하세요. Unity의 Build Settings에서 Platform Switch가 정상 동작하는지 확인하는 것과 비슷합니다.

### GitHub 연동 확인

Rider의 VCS 창에서 파일 변경사항이 정상적으로 추적되고 있는지 확인하세요. Unity Collaborate의 Changes 탭과 같은 기능입니다. GitHub에서 저장소가 생성되고 초기 커밋이 업로드되었는지 확인하세요.

## 🚀 다음 단계로의 연결

### Entity Framework Core 모델 생성 준비

환경 구축이 완료되었으니 이제 게임 데이터를 저장할 데이터베이스 모델을 만들 차례입니다. Unity의 ScriptableObject를 만들듯, Entity Framework에서는 Entity 클래스를 만들어 데이터베이스 테이블과 매핑합니다.

Player, Character, Item, OfflineReward 같은 게임 핵심 엔티티들을 하나씩 만들어가면서 방치형 RPG의 데이터 구조를 완성할 것입니다. Unity에서 GameObject와 Component를 설계하는 것과 매우 유사한 과정입니다.

### ASP.NET Core Web API 개발 시작

데이터 모델이 준비되면 Unity 클라이언트가 호출할 수 있는 Web API를 만들 것입니다. Unity의 MonoBehaviour가 Update(), Start() 같은 메서드를 제공하듯, Web API Controller는 HTTP 요청을 처리하는 메서드들을 제공합니다.

플레이어 생성, 로그인, 오프라인 보상 계산 같은 방치형 RPG의 핵심 기능들을 API로 구현하게 됩니다. Unity의 Network Manager와 비슷한 역할을 하지만 훨씬 더 강력하고 확장 가능한 방식입니다.

### Unity 클라이언트와의 연동

서버 API가 준비되면 Unity 클라이언트에서 HTTP 요청을 보내어 서버와 통신하는 시스템을 만들 것입니다. Unity의 UnityWebRequest를 사용하여 서버 API를 호출하고, JSON 데이터를 주고받는 방식입니다.

이는 Unity의 Addressable Asset System이나 Unity Services와 통신하는 것과 매우 유사한 패턴입니다. 차이점은 외부 서비스가 아닌 직접 만든 서버와 통신한다는 것뿐입니다.

## 💡 Unity 개발자를 위한 최종 조언

### 기존 경험의 적극적 활용

Unity에서 3년간 쌓은 경험은 서버 개발에서도 그대로 활용할 수 있습니다. Component 기반 설계, SOLID 원칙, 디자인 패턴에 대한 이해는 Clean Architecture를 학습하는 데 큰 도움이 됩니다. GameObject의 생명주기를 이해하고 계시다면 Entity의 생명주기도 쉽게 이해할 수 있습니다.

Unity의 Inspector에서 public 필드를 노출하는 것처럼, Web API에서는 DTO(Data Transfer Object)를 통해 클라이언트에 데이터를 노출합니다. Unity의 Serialization과 본질적으로 같은 개념이지만 HTTP와 JSON을 통해 네트워크로 전송된다는 차이가 있습니다.

### 점진적 학습의 중요성

Unity를 처음 배울 때도 GameObject 생성부터 시작해서 점진적으로 복잡한 기능들을 익혔을 것입니다. 서버 개발도 마찬가지로 간단한 API부터 시작해서 점진적으로 복잡한 시스템을 구축해나가는 것이 중요합니다.

한 번에 모든 것을 완벽하게 만들려고 하지 마세요. Unity에서도 프로토타입을 먼저 만들고 리팩터링을 통해 개선해나갔듯, 서버 개발에서도 동작하는 버전을 먼저 만들고 점진적으로 개선하는 것이 효과적입니다.

### 도구 친화성의 활용

JetBrains Rider를 선택한 이유는 Unity Editor와 유사한 사용자 경험을 제공하기 때문입니다. 새로운 도구를 배우는 스트레스를 최소화하고 핵심 개념 학습에 집중할 수 있게 해줍니다.

Docker Desktop, GitHub Desktop, pgAdmin 같은 GUI 도구들도 마찬가지입니다. 콘솔 명령어를 외우는 것보다 시각적 인터페이스를 통해 직관적으로 작업할 수 있어서 학습 효율성이 크게 향상됩니다.
